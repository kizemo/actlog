## 三、逐项结论与根因

### 3.1 drift(SQLite)

**结论：成立。** Windows 桌面端用 `NativeDatabase.createInBackground(File)` 直接开本地文件库，
`PRAGMA foreign_keys = ON` 必须在 `setup` 回调里**显式开启**（SQLite 默认关闭）。

⚠️ 两个会把人坑到怀疑人生的静默失败：

1. **part 文件名必须跟源文件同名。**
   `@DriftDatabase` 所在文件叫 `database.dart` ⇒ 必须写 `part 'database.g.dart';`。
   如果写成 `part 'database.g.dart';` 但源文件是 `main.dart`，drift_dev 会改去生成
   `main.g.dart`，**只在日志里留一句 warning**（`main.g.dart must be included as a part directive`），
   退出码仍是 **0**，但 `database.g.dart` 根本不生成 ⇒ 编译期报
   `uri_has_not_been_generated` + 一堆 `undefined_identifier`。
   *踩坑现场：codegen「成功」但产物缺失，退出码骗人。*

2. **`Table` / `Column` 在 drift 和 Flutter 里同名。**
   `import 'package:drift/drift.dart';` + `import 'package:flutter/material.dart';`
   同时存在时，`class ProbeRows extends Table` 会变成 `ambiguous_import` ⇒
   drift_dev 的分析器**认不出这张表** ⇒ 又是一次「只有 warning、没有产物」。
   消歧写法（本项目已采用）：
   ```dart
   import 'package:drift/drift.dart' hide Column;
   import 'package:flutter/material.dart' hide Table;
   ```

3. **drift 2.35 的 `count()` 返回 `Expression<int>`，没有 `getSingle()`。**
   要取单值得走 `Selectable`：
   ```dart
   final rows = await select(probeRows).get();
   return rows.length;
   ```

### 3.2 Windows 通知

**结论：成立，且不需要 MSIX 打包。**

- `flutter_local_notifications` 19.5.0 / `flutter_local_notifications_windows` 1.0.3，
  Windows 端是 **FFI + C++/WinRT** 实现（不是老的平台通道）。
- **19.5.0 起 `WindowsInitializationSettings` 的 `appName` / `appUserModelId` / `guid` 全部必填**，
  少一个编译不过。
- **`WindowsNotificationDetails` 已经没有 `appUserModelId` 参数**（AUMID 只在初始化时给一次）。
- 插件在 `registerApp()` 里会把 AUMID 写进
  `HKCU\Software\Classes\AppUserModelId\<aumid>`，所以**非 MSIX 的 exe 也能弹 toast**。
  MSIX 只影响「取回历史通知」（`cancel` / `getActiveNotifications`）——
  未打包时 `cancel` 无效、`getActiveNotifications` 返回空。
- AUMID 建议用 `Company.Product` 形式（本项目用 `com.actlog.actlog`；旧名 `com.practiclog.practiclog` 已于 Task 33 停用）。

### 3.3 托盘

**结论：成立。** `tray_manager` 0.2.4，`setIcon('assets/icon.ico')` + `setContextMenu` +
`setToolTip` 全部无异常；应用窗口关闭后进程存活、图标常驻。
（`assets/icon.ico` 需在 `pubspec.yaml` 的 `flutter: assets:` 里声明，否则打包后找不到。）

### 3.4 环境故障：VS 2026 C++ 工具链头文件损坏（本轮真实踩到）

**现象**：Flutter 打包时，`flutter_wrapper_plugin.vcxproj` 编译失败，
错误全在 MSVC 自己的 `<type_traits>` 里（`remove_reference_t` 未声明、
`bool_constant` 找不到标识符、`C2143` 语法错误），刷 100+ 条。

**根因**：**不是 Flutter 代码问题，也不是 C++ 标准版本问题。**
本机 VS 2026 BuildTools（MSVC **14.51.36231**）的
`VC/Tools/MSVC/14.51.36231/include/yvals_core.h` **首行被损坏**：

```
损坏态：EF BB BF 79 76 61 6C ...   ← UTF-8 BOM + "yvals_core.h internal header (core)"
正常态：EF BB BF 2F 2F 20 79 76 ... ← UTF-8 BOM + "// yvals_core.h internal header (core)"
```

开头的 `//` 注释符丢了，编译器把第一行当 C++ 代码解析，
于是 `yvals_core.h` 整体解析失败 ⇒ 后面所有 STL 符号连锁失效。

**判定方法（可复用的最短路径）**：不要在 Flutter 里试错，直接用**最小文件**探针：

```cpp
#include <type_traits>
int main(){ return sizeof(std::remove_reference_t<int>); }
```
配合 `cl /std:c++17 /std:c++20 /std:c++latest` 各编译一次。
四种标准全挂 ⇒ 问题在工具链，不在项目代码。

**修复**：备份原文件后，在 BOM 之后补回 `// ` 两个字符即可（本项目已完成）。
备份留在 `tools/spike/backup/yvals_core.h.14.51.36231.corrupt.bak`。

**旁证**：同机 VS 2022 BuildTools（MSVC 14.44.35207）的同名文件**完好**，
⇒ 属于 14.51 这版安装的个别文件损坏，不是系统性问题。

> ⚠️ 教训：**「C++ 编译报 STL 头文件语法错」的第一嫌疑是工具链，不是自己的代码。**
> 先用最小文件探针把「工具链」和「项目代码」分开，再往下查。

### 3.5 打包阻塞：VS 缺 ATL → MSB8041（已用「借用」方案零安装绕过）

修好 STL 头文件后，`flutter build windows --release` 撞上第二个坑：

```
error MSB8041: 此项目需要 ATL 库。请安装适用于最新 v143 生成工具的 C++ ATL
（或适用于 v142 的 C++ ATL 和适用于 v141 的 MFC）。
...\flutter_local_notifications_windows.vcxproj
```

**根因**：`flutter_local_notifications_windows` 1.0.3 的 `src/plugin.cpp:5`
**无条件** `#include <atlbase.h>`（实际只用到 `atlconv.h` 里的 `CW2A` 模板）。
而本机 VS 2026 BuildTools 没装 ATL 组件。

**★ MSB8041 的真实触发条件**（`Microsoft.CppBuild.targets:506`，反编译式定位过）：

1. `Link.AdditionalDependencies` 里包含 `atls.lib`，**并且**
2. `$(ATL_KeyFile)` 指向的文件不存在 ——
   `ATL_KeyFile` = `$(VCToolsInstallDir)atlmfc\lib\<spectre>\<plat>\atls.lib`，
   定义在 `Microsoft.Cpp.VCTools.Content.props:186`。

这套判定只认**它自己安装目录下的** ATL。因此：

> ❌ 把本机别处找到的 `atls.lib` 塞进 `target_link_libraries(...)` **反而必然触发 MSB8041**，
> 因为它会被写进 `Link.AdditionalDependencies`，而 `ATL_KeyFile` 那条路径依然不存在。
> 这是本轮最反直觉的一个点 —— 「补上缺的库」这个直觉动作，在这里是错的。

**已采用的方案（免安装，零系统改动）**：只给编译器**找头文件和找库的目录**，
不声明任何 ATL 库为链接依赖。`atlbase.h:118` 自带
`#pragma comment(lib, "atls.lib")`，链接器会沿库搜索目录自己找到它。

补丁写在 `apps/spike_d1/windows/CMakeLists.txt` 的
`include(flutter/generated_plugins.cmake)` **之后**：

```cmake
# 探测本机任何装了 ATL 的 VS 版本（VS2022 与 VS2026 并列时也能挑对）
file(GLOB _plog_atl_candidates
  "C:/Program Files (x86)/Microsoft Visual Studio/*/*/VC/Tools/MSVC/*"
  "C:/Program Files/Microsoft Visual Studio/*/*/VC/Tools/MSVC/*")
# 逐个判 atlmfc/include/atlbase.h + atlmfc/lib/x64/atls.lib 都存在，
# 取 MSVC 版本号最高的一套，只加 include dir 与 link dir。
```

**为什么用 `file(GLOB)` 而不是写死路径**：本机同时装着 VS 2022（MSVC 14.44.35207，
ATL 完好）和 VS 2026（MSVC 14.51.36231，无 ATL）。写死版本号会在任一端升级后失效。
GLOB 后按版本号取最高**可用**的那套，VS2026 一旦补装 ATL 会自动切回。

**顺带解决的 STL1011**：`<experimental/coroutine>:36-40` 要求定义
`_SILENCE_EXPERIMENTAL_COROUTINE_DEPRECATION_WARNINGS`，
否则插件的协程用法直接是**硬错误**（不是 warning）。已对该插件 target 加 `PRIVATE` 定义。

> 本条结论**不需要用户安装任何系统组件**，原先准备的「申请给 VS2026 补装 ATL」不再需要。

## 四、本轮沉淀的验收方法

`tools/spike/d1_verify.ps1` —— **机器判定**，不依赖人肉点按钮：

1. 清掉上次的库文件与日志；
2. 启动 exe，等到日志出现 `SELFTEST END ALL_OK`（或 `SELFTEST FAILED`）；
3. 断言：通知初始化 / 通知弹出 / 托盘初始化 / 库打开 / 库写入 五个 STEP 全 OK；
4. 断言：库文件落盘、**进程仍存活**（托盘常驻）、AUMID 注册表键存在、行数 ≥1；
5. 杀掉进程，**再启动一次**，断言行数**累加** ⇒ 证明「重启后数据仍在」。

> 应用侧配合：原型启动即自动自检，并把每一步写进
> `%APPDATA%\com.practiclog\spike_d1\spike_d1_log.txt`。

### 4.1 踩到的坑：验收脚本读「追加型日志」会被上一轮的完成标记假命中

**首次运行是 10/11**，唯一失败项是「重启后行数累加 run1=1 -> run2=1」。

第一反应是「drift 持久化失败」，但取证后定性为**脚本缺陷**：日志是**追加写**的，
第 2 次启动时脚本读到的第一个 `SELFTEST END ALL_OK` 来自**第 1 次运行**，
于是它立刻跳出等待循环、2 秒后把进程杀掉 —— 而第 2 次自检当时才刚跑到
`STEP_TRAY_INIT OK`，`STEP_DB_WRITE` 根本没执行，行数自然没涨。

**修法**：启动前记录日志文件的字节长度 `$before`，之后只匹配「本次新增」的那一段
（`FileStream` + `Seek($before)`），轮询间隔 300 ms，读到标记后再等 1 s 收尾。

> ⚠️ 可复用教训：**验收脚本读追加型日志时，必须用「启动前字节偏移」切出新段。**
> 否则「上一轮的完成标记」会冒充「本轮的成功」，而且它会以「功能失败」的形态出现，
> 把你引向完全错误的方向。这类假失败比假通过更浪费时间。
