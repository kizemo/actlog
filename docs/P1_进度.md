## 里程碑 1：业务逻辑层 `packages/core_data` 完成（2026-11-06）

### 为什么单独建一个纯 Dart 包

G1（`tools/gates/g1_analyze.ps1`）与 G2（`tools/gates/g2_unittest.ps1`）只**自动发现 `packages/` 下含 `pubspec.yaml` 的目录**，
不扫 `apps/`。P1 的验收标准里多处写着「有单测」（P1-2 三段自动生成逻辑、P1-8 失守标记规则），
把规则放 `apps/desktop` 里等于让这些验收永远无法被机器判定。
因此：**规则与仓储层 → `packages/core_data`（纯 Dart，进门禁）；渲染与状态 → `apps/desktop`（Flutter）。**

### 交付物

| 文件 | 作用 |
|---|---|
| `packages/core_data/pubspec.yaml` | `resolution: workspace`；依赖 `core_db`/`core_domain`/`drift` |
| `lib/src/support.dart` | `uuidV7`（RFC 9562）、`nowMillis`、`isoDate`/`today`/`parseIsoDate`/`shiftIsoDate`/`previousIsoDate` |
| `lib/src/models.dart` | `StandupSource`(6 值)、`StandupEntry`、`StandupBrief`、`MoodSummary`、`ReviewDraft` |
| `lib/src/priority.dart` | `QuadrantStyle`/`AbcStyle`/`PriorityDisplay`（表头文案、标签、排序权重） |
| `lib/src/standup.dart` | `StandupBuilder`：昨日亮点 / 今日优先 / 阻塞项 三段纯函数生成 + `StandupConfig` |
| `lib/src/mood.dart` | `MoodRules`：分数域校验、失守只开不关、8 维 ↔ 列映射 |

### 本轮修掉的真实缺陷

**`HabitRepository.upsertCheckin` 墓碑撞唯一约束。**

`docs/schema_v1.sql:260` 的 `habit_checkin_pair_unique UNIQUE (habit_id, date)` **不带**
`WHERE deleted_at IS NULL` 的部分索引 ⇒ 软删的行仍占着槽位。
原实现用带墓碑过滤的 `findCheckin` 查重，于是「撤销打卡 → 同一天再打卡」会走 insert 分支、撞唯一约束抛错。

修法与 `SettingsRepository.set` 对齐：新增不过滤墓碑的 `_checkinRow` 用于写路径，
复活时把 `deleted_at` 显式置回 NULL（保持 id 稳定 —— 对端同步是 update 而不是 delete+insert）。
**不动 schema**（schema v1 已冻结，改它等于 v2 + 迁移脚本）。

### 本轮修掉的真实缺陷

1. `habit_section.dart` / `standup_section.dart` 各有一个未用 import（analyze warning）。
2. `HabitData.targetCount` 是 **`double?`** 不是 `int` ⇒ `habit.targetCount > 1` 报 `unchecked_use_of_nullable_value`。
   修法：先取局部变量判空，整数不显示小数位（`% 1 == 0`）。
3. **`review_section.dart` / `mood_section.dart` 的 `dispose()` 里读 `ref` —— 真实运行时缺陷。**
   两个区块都在 `dispose()` 里调 `_persist()` → `ref.read(repositoriesProvider)`，
   而 Riverpod 在 widget 卸载时抛
   `Bad state: Using "ref" when a widget is about to or has been unmounted is unsafe.`
   ⇒ **关窗/切页会炸**，不只是测试问题。
   修法：把仓储实例在 `build()` 里捕获进 `_repo` 字段（`_repo ??= ref.read(...)`），
   `dispose()` 只用字段；落库逻辑抽成 `_persistTo(DayLogRepository repo, String logId)`，
   把「怎么拿到仓储」与「落库」解耦。

### 端到端测试：从「挂死」纠正为「快速失败」

> 原判断「3 个用例挂死」是**误判**。真相：4 个用例都在 2 秒内抛异常失败，
> 但 `flutter test` 报错后继续跑剩余用例、输出被缓冲，看起来像挂死；
> 400s 命令上限是被 3×90s 单测超时耗尽的，不是死锁。

**根因（两个，都已修）**：

1. 上述 `dispose()` 读 `ref` 的缺陷 ⇒ P1-1 / P1-5 / P1-6 全被它打挂。
2. **测试断言歧义**：`find.text('某条目标题')` 同时命中**输入框里的文本**、**列表项**，
   以及**站会区块的「今日优先」**（它也列出今天的计划条目）⇒ 命中 2 个。
   修法：新增 `_inPlanBlock(text)` 辅助函数，把范围钉死在「今日计划」这张 `SectionCard` 里
   （`find.descendant(of: find.ancestor(of: find.text('今日计划'), matching: find.byType(SectionCard)), ...)`）。

**收尾噪声（非产品缺陷）**：drift 的 `StreamQueryStore.markAsClosed` 会在 StreamProvider 被 dispose 时
排一个 **0 长度 timer**，测试框架在「widget 树销毁后还有 pending timer」时判
`A Timer is still pending even after the widget tree was disposed.`。
修法：`_flushTimers(tester)` —— 先 `pumpWidget(SizedBox.shrink())` 销毁树（触发 Provider 销毁排 timer），
再 `pump()` + `pump(1ms)` 把 timer 跑完。
**必须写在用例体内，不能挂 `addTearDown`**：框架的 `_verifyInvariants` 在 tearDown **之前**就检查 timer。

### 另一个坑：并发测试任务占用 sqlite3.dll

前一个测试任务没退干净时，残留的 `flutter_tester.exe` 会锁住
`apps/desktop/build/native_assets/windows/sqlite3.dll`，下一个 `flutter test` 直接失败：
`Flutter failed to delete file at "...sqlite3.dll". The flutter tool cannot access the file or directory.`
⇒ **每次复跑前先确认没有残留的 `dart` / `flutter_tester` 进程**；
复跑失败时先看是不是这个，而不是怀疑测试逻辑。

- `flutter analyze` → `ANALYZE_EXIT=0`，`No issues found! (ran in 14.1s)`。
- `flutter test`（全量）→ `TEST_EXIT=0`，**16 例全绿**

  `sqlite3.dll`(1,731,072) + `flutter_local_notifications_windows.dll`(90,112) + `dartjni.dll`(58,368)。

### 关键决策

- **`_PlanBlock` 内用 `Column` 而非 `ListView.builder`**：外层已是 `ListView`，嵌套滚动会出问题；一天条目数有限。
- **优先级展示模式切换放在「今日计划」区块的 `trailing`**（`TextButton.icon`），不放 AppBar ——
  AppBar 已有完整/极简切换，两个 `SegmentedButton` 会挤爆。
  表头联动用 `subtitle: PriorityDisplay.headerHint(displayMode)` 实现。
- **`displayMode` 读不出来时按 `quadrant` 渲染**：四象限是自由度更高的那一种，退到它不会让已填的 ABC 数据看起来「丢了」。
- **成果回填走「整行点击 → 对话框 → 三按钮（取消/只存进展/完成）」**；
  `_ResultEdit` 包装类携带 `done` 意图，避免「只存进展」被误当成完成。
- **只有 `promote` 能把习惯回填行转成普通条目，不提供反向操作** ——
  「普通条目变回习惯行」后习惯本身对不上账。
- **UI 行为测试只测不需要 DB 的组件**（两个选择器 + 标签）；互斥性/不丢数据原由 `core_data` 的 107 例兜底，
  现已确认可加端到端层。

### 未验证 / 已知问题（下一步要处理）

**已排除的原因**：`pumpAndSettle` 挂死（加载态的 `CircularProgressIndicator` 是无限动画）——已改成

**下一步要查的方向**（未验证）：

### 关键决策

1. **「关窗隐藏到托盘」在 runner（C++）层实现，不在插件层。**
   插件层的 `setPreventClose(true)` **只拦插件自己发起的 close**；Windows 关闭按钮发的是
   raw `WM_CLOSE`，会走到 `DefWindowProc` → 销毁窗口 → `WM_DESTROY` → `PostQuitMessage` → 进程退出。
   所以 Dart 通过 `MethodChannel('practilog/window')` 的 `setHideOnClose` 让 runner 自己接管 `WM_CLOSE`。
   （插件层 prevent close 保留，管 Dart 侧发起的 `close()`。）

2. **中文标题走 Dart 侧 `windowManager.setTitle`**，不往 C++ 里写中文 ——
   Flutter Windows 模板的 `main.cpp` 没有加 `/utf-8`，非 ASCII 源码会按本地代码页编译。

3. **「启动即自检」默认不跑**：仅 `--selftest` / `--selftest=*` / `PRACTILOG_SELFTEST=1|true|yes` 才跑，
   写报告并以退出码返回。真实库只读，写操作在临时库 `practilog_selftest.db`，跑完即删。

4. **自检报告增量落盘**（每条检查后写一次，末尾写 `RESULT`）：中途崩溃也能定位卡在哪一步。

5. **启动链路每一步独立 try/catch 兜底**；新增 `practilog_startup.log` 作为 GUI 程序唯一的启动现场证据。
   日志用**串行 Future 链**写入（两个句柄并发 append 会互相覆盖，本轮实测丢过一行 `tray ready`）。

6. **窗口/托盘的先后依赖是硬约束**：托盘建不起来时**不能**拦截关窗，
   否则用户点关闭后既看不到窗口也没有托盘可点，进程变成既关不掉又看不见的僵尸。

### 本轮修掉的真实缺陷（3 个）

1. **Flutter C++ 客户端 API 用错，导致 release 构建失败**。
   `flutter_controller_->engine()->binary_messenger()` **不存在**（正确是 `messenger()`）；
   `MethodChannel` 构造函数需要三个参数（`messenger, name, codec`），
   少传 codec 会报 `C2661: 没有重载函数接受 2 个参数`。
   修法：改用 `engine()->messenger()`，并传 `&flutter::StandardMethodCodec::GetInstance()`。

2. **`-Teeth` 反向验证**取退出码/日志的方式不对，让「有牙」检查**静默失效**：
   用 `& $flutter ... *>&1 | Out-File` 调 `.bat` 时，退出码与输出都拿不到（拿到空日志），
   断言还因 `System.Object[] → Boolean` 转换错误而整段中断。
   修法：改用 `Start-Process` + `RedirectStandardOutput/Error` + `ExitCode`；
   并把失败形态断言放宽为同时接受 **C1083**（编译期找不到 `atlbase.h`）与
   **LNK1104**（增量构建下插件 obj 仍在，只走到链接找不到 `atls.lib`）——
   两者都表示「没有借用就没有可用 ATL」。

3. **`apps/desktop` 的 analyze 报错** `use_of_void_result`：
   `Completer<void>` 上写 `.then((value) => value != null)`。
   修法：改用 `Completer<bool>` + `onTimeout: () => false`。

## 里程碑 6：§16.5 托盘交互 / toast 真机验证（2026-11-07 第五次会话）

### 目标

把 `docs/P1_交接文档.md` §16.5 的四条「仍未验证」逐条变成**脚本化真机证据**：
托盘左键切换、右键菜单 +「显示窗口」拉回、toast 可见、SFX 真机安装。

### 关键根因：托盘菜单为什么「弹不出来」

第一轮走的「跨进程向托盘回调窗注入消息」路线**整体作废**，根因是回调窗是
**message-only 窗口**：`cnativeapi` 的 `WindowMessageDispatcher::GetHostWindow()` 用
`HWND_MESSAGE` 作父窗口创建 `NativeApiHostWindow`。实测 `EnumWindows` /
`EnumChildWindows(HWND_MESSAGE)` / `FindWindowEx(HWND_MESSAGE, ...)` /
「桌面窗口里 `GetParent()==HWND_MESSAGE`」四种查法在别的进程里**全部返回空** ——
不是「窗口不存在」，而是这种窗口按设计就不可跨进程枚举。
⇒ 唯一可信判据是**真实鼠标点击真实托盘图标**（shell → app 全链路），脚本改成这条路。

打通后又暴露一个**真实缺陷**（本轮修掉，且**纠正了上一轮的错误结论**）：

> `tray_manager 0.8.3` 的 `setContextMenu()` **只在 Linux 分支**里把
> `contextMenuTrigger` 设成 `rightClicked`；Windows 上原生默认是 `None`
> （`cnativeapi/src/tray_icon.h` 明写「requiring explicit control via
> `OpenContextMenu()`」）。
> ⇒ 右键菜单**必须由 Dart 侧显式调 `trayManager.popUpContextMenu()`**。

上一轮把 Dart 侧这行当「原生会重复弹菜单」删掉了 —— 那个前提是错的（Windows 上原生根本不自动弹），
结果等于把右键菜单关掉了。**本轮恢复该调用后一次通过**，`menu_windows_seen = 1` 证明只有一层菜单。
⚠️ **下一轮不要再删这行**。

### 本轮踩过的坑（脚本级，避免重犯）

1. **PowerShell 委托回调里的累加器必须放 `$script:` 作用域**。
   `Get-VisibleTops` 原先把列表写成函数局部 `$t`、回调里却写 `$script:t` ⇒ `$null.Add()`
   抛「不能对值为 Null 的表达式调用方法」，`EnumWindows` 整段炸掉。
2. **托盘图标 tooltip 与主窗口标题同名**（都是「知行日志」）。
   只按 Name 找会误匹配 Flutter 窗口 ⇒ 必须叠加「通知区 AutomationId + 与主窗口矩形不重叠」过滤。
3. **菜单项坐标**：`GetMenuItemRect()` 传 HMENU 对弹出菜单返回**全 0 矩形**（拿到就点了 (0,0)）。
   取屏幕坐标要传**菜单窗口句柄**，或改用 UIA / 几何估算 —— 脚本里做了三级兜底
   （`GetMenuItemRect(menuWnd)` → UIA → 按菜单窗矩形均分）。
4. **窗口枚举轮询太慢**：每次 `EnumWindows` + 逐窗取类名/进程约 15–30ms，够不上「菜单只活几十毫秒」的窗口。
   改用单次 `FindWindow('#32768')` 轮询后，菜单在 14–24ms 内就被抓到。
5. **目录列举/字符串拼接**：老坑仍在 —— 用 `Join-Path`、避免含 `(build|\.dart_tool)` 的正则。
