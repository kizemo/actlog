## 0. 摘要

把 PractiLog 从「**深色档 == 浅色档**」变成一套完整、刻意、可机器验证的深色主题。

## 1. 为什么必须独立做（现状取证）

### 1.1 深色档 == 浅色档

`app_theme.dart:24-118` 的 `_build(density, brightness)` 对两档走同一条路径：`ColorScheme.fromSeed(...)` 之后把 **24 个 slot 全部覆盖成浅色常量**（`:29-52`）。所以设置页的「深色」能切、渲染结果与浅色逐字节相同。

### 1.2 更深的问题：半深半浅

`ColorScheme` 在本机 SDK（engine `89c39edfdfae2949f6806e4a315c0c08522238b7`）公开 **50 个字段**，现状只覆盖 24 个 ⇒ **剩 26 个随 `fromSeed` 按 brightness 自动派生**。

再往上，`ThemeData.copyWith` 共 81 个形参，其中与亮度相关的默认派生（本机 `theme_data.dart` 构造器 `??=` 段实测）：

- 从 colorScheme 派生：`canvasColor` / `scaffoldBackgroundColor` / `cardColor` / `dialogBackgroundColor` / `dividerColor` / `indicatorColor` / `primaryColor` / `primaryColorDark` / `primaryColorLight` / `iconTheme` / `primaryIconTheme` / `primaryTextTheme` / `textTheme`
- 透明度派生（实施时须逐字段核对 SDK 默认值）：`focusColor` / `hoverColor` / `highlightColor` / `splashColor` / `disabledColor` / `hintColor` / `unselectedWidgetColor` / `shadowColor` / `secondaryHeaderColor`
- 布尔：`applyElevationOverlayColor`

> **顺带发现的一个既有缺陷**：SDK 写的是 `applyElevationOverlayColor ??= brightness == Brightness.dark`，取的是**构造参数** `brightness` 而不是 `effectiveBrightness`。本项目 `ThemeData(useMaterial3: true, colorScheme: scheme)` 从不传 `brightness` ⇒ **两档的 elevation overlay 都是关的**。Task 41 顺带把深色档显式钉死。

结论：**只加第二套色值是不够的**，必须同时把「色板来源」「ColorScheme 装配」「ThemeData 装配」三层一起改，否则必然产出半深半浅的半成品 —— 这正是计划 §40.7 说的「混轮必然半深半浅（R5 禁半成品）」。

## 3. 架构决策

### 3.1 决策 A —— 颜色全部迁出 `AppTokens`（**编译器强制「不可能半成品」**）

现状 `AppTokens` = 27 色 + 9 尺寸。改造后：

- **`AppTokens` 只保留 9 个尺寸 token**：`radius` / `gapCard` / `gapSec` / `tlWidth` / `tlGap` / `tlWidthNarrow` / `tlGapNarrow` / `axisTickHour` / `axisTickHalf`。
  尺寸与亮度无关，保持 `static const` ⇒ **158 处尺寸引用零改动**。
- **28 个颜色 token 全部迁出**到新文件 `apps/desktop/lib/src/theme/theme_tokens.dart`（27 个原有 + 新增 1 个 `shadowTint`）。

**为什么这是本设计的核心**：迁出之后，任何「静态引用浅色」的代码路径**直接编译失败**。这不是靠人工纪律，是靠编译器。R5「禁制造『已交付』假象」由此从口号变成结构性保证 —— 深色档想做出半成品都编译不过。

### 3.2 决策 B —— `ThemeExtension` 承载解析式 token 包

```dart
// apps/desktop/lib/src/theme/theme_tokens.dart
class ThemeTokens extends ThemeExtension<ThemeTokens> {
  const ThemeTokens({ /* 28 个 final Color 字段 */ });

  static const ThemeTokens light = /* 逐字等于今天的 AppTokens.* */;
  static const ThemeTokens dark  = /* §4 的暖墨深褐 28 色 */;

  static ThemeTokens of(BuildContext context) =>
      Theme.of(context).extension<ThemeTokens>() ?? ThemeTokens.light;
}

extension ThemeTokensContext on BuildContext {
  ThemeTokens get tokens => ThemeTokens.of(this);
}
```

- `ThemeTokens.light` 的每个字面量**逐字等于**今天的 `AppTokens.*` ⇒ **浅色渲染零变化**（既有 203 处硬等断言继续成立）。
- `ThemeTokens.dark` 是本设计的新色板。
- **兜底浅色**：`Theme.of(context).extension<ThemeTokens>()` 在裸 `MaterialApp()` 的既有 widget 测试里是 null ⇒ 回落 `ThemeTokens.light`，既有测试不炸。
- **别名链保持**：`slotPlanInk` / `slotBackfillInk` / `slotHabitInk` = `ink`；`slotDoneInk` = `meta`；`gridSectionMorning/Noon/Evening` = `card`/`paper`/`sunken`。在包内用私有 `static const` 承载，使 `light` 与 `dark` 各自保持别名一致（避免「格底去蓝、格内文字仍蓝」式的半截改动）。
- `copyWith` / `lerp` 必须实现（`ThemeExtension` 抽象方法，且 `MaterialApp` 默认 `AnimatedTheme` 会调 `lerp`）。

**为什么不用「按 `Theme.of(context).brightness` 推断」**：`ThemeExtension` 把解析后的色板**随 `ThemeData` 一起传下去**，渲染点拿到的就是装配时选定的那一套，不会出现「brightness 翻转了但 ColorScheme 还在插值」的错位；且不引入任何全局可变状态。代价是 28 字段的 `copyWith`/`lerp` 样板 —— 机械、可测。

### 3.3 决策 C —— 深色 `ColorScheme` 逐字段钉死 **47 个现役字段**

`ColorScheme` 公开 50 个字段，其中 **3 个已 `@Deprecated`**（本机 SDK 实测）：

| 废弃字段 | 替代 | 处置 |
|---|---|---|
| `surfaceVariant` | `surfaceContainerHighest` | **不设值** |
| `background` | `surface` | **不设值** |
| `onBackground` | `onSurface` | **不设值** |

> 设值会触发 `deprecated_member_use`（analyzer **info** 级）⇒ 直接破「`flutter analyze` 逐字 `No issues found!`」门禁。这 3 个字段在 `fromSeed` 里由 `surface`/`onSurface`/`surfaceContainerHighest` 派生，而那 3 个我们已钉死 ⇒ 不会构成半深半浅。

**深色档 47 字段映射表（实施时逐条落地；左列 24 项 + 右列 23 项 = 47，无重复、无遗漏）**：

| ColorScheme 字段 | 深色取值 | ColorScheme 字段 | 深色取值 |
|---|---|---|---|

| `primary` | `ink` | `error` | `accentInk` |

| `primaryContainer` | `inkWash` | `errorContainer` | `accentWash` |
| `onPrimaryContainer` | `ink` | `onErrorContainer` | `accentInk` |
| `primaryFixed` | `ink2` | `surface` | `paper` |
| `primaryFixedDim` | `meta` | `onSurface` | `ink` |

| `onTertiaryFixed` | `paper` | | |

**取值约定**（三条，逐条可验）：

1. **明暗反转在 token 层完成**：深色档里 `ink`/`ink2`/`meta`/`faint` 是浅色暖米白，`paper`/`card`/`sunken` 是深色暖墨褐 ⇒ 颜色槽的「前景/背景」关系整体翻转，与浅色档的语义分工一一对应。
2. **容器槽梯度单调不减**：`surfaceContainerLowest`(`sunken`) < `surface`(`paper`) < `surfaceContainerLow`(`card`) = `surfaceContainer` = `surfaceContainerHigh` = `surfaceContainerHighest`(`card`)。后四级同值是**有意压缩**：28 色板内没有比 `card` 更亮的中性色，为凑满 M3 五级梯度而新增 token 会让调色板膨胀并连带重算全部对比度证据 ⇒ 不做。压缩后仍满足「比 surface 更亮 = 抬起」的语义，且没有任何一级比 surface 更暗（`Lowest` 除外，它按 M3 语义就是最深的容器）。
3. **前景/背景配对自洽**：`onPrimary`/`onSecondary`/`onTertiary`/`onError`/`onInverseSurface` 一律取 `paper`（深色档的 `paper` 是**深**墨褐），`onSurface`/`onInverseSurface` 的底一律是浅色墨 ⇒ 任何「亮底 + 亮字」的错配都不会出现。

**浅色档**保持现状（只覆盖那 24 个 slot，其余继续走 `fromSeed`）⇒ 浅色渲染逐字节不变。

### 3.4 决策 D —— 深色 `ThemeData` 亮度敏感字段显式钉死

§1.2 列出的字段（`canvasColor` / `cardColor` / `dialogBackgroundColor` / `dividerColor` / `indicatorColor` / `primaryColor` / `primaryColorDark` / `primaryColorLight` / `focusColor` / `hoverColor` / `highlightColor` / `splashColor` / `disabledColor` / `hintColor` / `unselectedWidgetColor` / `shadowColor` / `secondaryHeaderColor` / `applyElevationOverlayColor` / `iconTheme` / `primaryIconTheme` / `primaryTextTheme`）在**深色档一律显式给定**，取值来自 `ThemeTokens.dark`。

- 透明度派生字段一律用 `withValues(alpha: …)`；**不得用 `withOpacity`**（Flutter 3.27+ 已废弃，用了会触发 `deprecated_member_use`）。
- `applyElevationOverlayColor` 深色显式给 `true`（现状因 SDK 取参 bug 两档都是 false）。
- 浅色档保持现状不动。

### 3.5 决策 E —— 组件主题策略维持「token 口径只有一处」

维持 `app_theme.dart` 既有注释的立场：**不设** `cardTheme` / `dialogTheme` / `chipTheme`（这几个类的类型在 Flutter 3.47 小版本间摇摆，写死会炸编译）。卡片 / 芯片 / 弹层外观继续在各自 widget 里显式引用 token。

### 3.6 被否决的方案

| 方案 | 否决理由 |
|---|---|
| **全局静态调色板**（`AppTokens.current` 可变全局） | 全局可变状态；`AppTheme.dark` 构造会污染同文件后续用例；非 Flutter 惯用法；违背 `TOKENS.md`「token 口径只有一处」的注释精神。 |
| **只改 60 处 `const` 色值** | 覆盖不到 581 处引用中的绝大多数（多数是运行期取值），改完仍是半深半浅。 |
| **保留 `AppTokens` 颜色双轨**（浅色留在原地，深色另起一份） | 静态浅色常量仍可被随手引用 ⇒ 靠纪律而非靠编译器防半成品。与决策 A 冲突。 |
| **`Theme.of(context).brightness` 推断代替 `ThemeExtension`** | 插值期与装配期可能错位；且不带包（见决策 B）。 |

### 4.3 结构性证据：深色**复刻**了浅色的视觉层级

这不是「把浅色调暗」：

- **四态可分离度逐对几乎相同** —— 深色 1.061/1.052/1.158/1.116/1.228/1.100 vs 浅色 1.118/1.004/1.106/1.122/1.236/1.102。深色整体还略优于浅色（浅色的 `plan/backfill` 只有 1.004，几乎撞色）。
- **每个文字色的最差场景深色都更好**（判据 13）。
- 唯一的次序反号是 `card` vs `paper`：`card` 在两档里都是「抬起」（更亮），但 `ink` 明暗反转 ⇒ 文字压在 `card` 上与压在 `paper` 上的对比度大小次序**必然反号**。这是几何必然，不是缺陷 —— 差值 0.13，在 13:1 的量级上不可感知。

## 5. 主题装配

`AppTheme._build(density, brightness)` 改为按亮度分流：

```
ThemeTokens.ofBrightness(Brightness.light) → ThemeTokens.light
ThemeTokens.ofBrightness(Brightness.dark)  → ThemeTokens.dark
```

- 浅色档：`copyWith` 24 个 slot（取值 = `ThemeTokens.light.*`，逐字等于今天的 `AppTokens.*`）+ 9 个 TextTheme 角色 + `dividerColor` + `scaffoldBackgroundColor` + `extensions: [tokens]`。
- 深色档：**47 个 ColorScheme 字段全钉**（§3.3）+ 9 个 TextTheme 角色 + `dividerColor` + `scaffoldBackgroundColor` + §3.4 的 ThemeData 字段 + `extensions: [tokens]`。
- 9 个 TextTheme 角色：`bodyLarge`/`bodyMedium`/`bodySmall`/`titleLarge`/`titleSmall` = `ink`；`labelLarge`/`labelMedium` = `meta`；`labelSmall` = `faint`。深色自动取 `ThemeTokens.dark` 的对应值。
- `app.dart:109-111` 的接线**不动**：`theme: AppTheme.light(prefs.density)` / `darkTheme: AppTheme.dark(prefs.density)` / `themeMode: prefs.themeMode`。
- 设置页三枚 `_ChoiceChip`（`settings-theme-system` / `-light` / `-dark`）**不动**。
