### 1.4 数据层：三张表 + 两条外键，全部已存在

这是本次规划最重要的事实：**项目功能所需的表结构在 FROZEN 的 `docs\schema_v1.sql` 里全部就位。**
Task 40 的硬约束是「零 schema 变更 / 零新依赖」，本项目在数据层**完全满足**。

| 表 | 建表位置 | 关键列 | 索引 |
|---|---|---|---|
| `project` | `docs\schema_v1.sql:298` | `name` / `goal` / `start_date` / `end_date` / `domain` / `status` / `archived` | `idx_project_status`、`idx_project_updated_at` |
| `project_milestone` | `docs\schema_v1.sql:321` | `project_id` / `title` / `target_date` / `achieved_at` / `note` | `idx_project_milestone_project`、`idx_project_milestone_target_date` |
| `project_increment` | `docs\schema_v1.sql:343` | `project_id` / `date` / `plan_item_id` / `progress` / `blockers` / `next_step` | `idx_project_increment_project_date`、`idx_project_increment_date` |

约束细节（同样已存在，不需要新建）：

- `project.status` 有 CHECK：`'active' | 'paused' | 'done' | 'cancelled'`（`:312` 附近）。
- `project.archived` 有 CHECK：`0 | 1`，即**归档是独立于状态的第二维**。
- `project_milestone.project_id` 与 `project_increment.project_id` 都是 `REFERENCES project (id) ON DELETE CASCADE`。

`project_increment` 的建表注释（`:344-345`）直接写明了产品意图，本文的交互设计应当照抄而不是另创：

> 「项目增量记录（同步，「不闭环」日志）—— 每次推进只追加一条，不修改历史；连续 3 天无增量触发温和停滞提示。」

### 1.5 两条既有的关联通道（决定联动模型）

| 通道 | 位置 | 形态 | 能否支撑「项目 → 今日」 |
|---|---|---|---|
| `todo.project_id` | `docs\schema_v1.sql:176`；FK `:190`；索引 `:195` | 待办池条目直挂项目 | 能，**单向**（待办 → 项目） |
| `plan_item.source_type` / `source_id` | `docs\schema_v1.sql:127-128`；`CHECK` 含 `'project'` 与 `'increment'` | 多态指针 + 索引 `idx_plan_item_source` | 能，**排期条目 → 项目/增量** |
| `project_increment.plan_item_id` | `docs\schema_v1.sql:347`；FK 指向 `plan_item(id) ON DELETE SET NULL` | 增量 → 排期条目 | 能，**反向指回** |

**关键负面事实**：`plan_item` **没有** `project_id` 列（`docs\schema_v1.sql:122-146` 全列已核）。
所以「某条计划属于哪个项目」**只能**经由 `source_type='project' | 'increment'` + `source_id` 表达。
这不算缺陷 —— 索引 `idx_plan_item_source` 就是为这个查询建的 —— 但它意味着：

> 任何「项目页里列出该项目的今日排期」的查询，**必须**写成
> `WHERE source_type = 'project' AND source_id = ?`，**不能**写成 `WHERE project_id = ?`。
> 写成后者会静默返回空列表，而不是报错。这是本项目最容易踩的一个坑，必须写进实现的注释里。

## 2. 信息架构

### 2.1 三层结构

```
项目（project）
├── 项目清单            ← 导航落点（nav id: 'projects'）
│   ├─ 按状态分组：active / paused / done / cancelled
│   ├─ 归档折叠区（archived = 1，默认收起）
│   └─ 每行：名称 · 目标一句话 · 进度（里程碑达成 x/y）· 最近增量距今 N 天
│
└── 项目详情（点行进入，壳内二级视图，不 push 新路由）
    ├─ 头部：名称 / 目标 / 起止日期 / 状态徽标
    ├─ 里程碑区（project_milestone）
    │   ├─ 列表：title · target_date · achieved_at（未达成 = 空）
    │   └─ 动作：标记达成 / 改目标日期 / 加一条
    ├─ 增量流（project_increment，**只追加，不改历史**）
    │   ├─ 每次一条：date · progress · blockers · next_step
    │   └─ 空态：引导写第一条增量（不是"暂无数据"）
    └─ 关联区（两条通道各一段）
        ├─ 该项目的待办（todo.project_id）
        └─ 该项目的排期（plan_item WHERE source_type='project'/'increment'）
```

### 2.2 为什么详情不用独立路由

`app.dart:150-160` 已确立壳的纪律：「导航点击只切本组件的 `_nav` 状态，不做路由 push —— 否则每点
一次就叠一层壳」。项目详情属于**同一页的纵深**，用壳内二级状态（`_nav == 'projects'` 时再持一个
`_selectedProjectId`）表达，**不**新增 `MaterialApp.routes` 分支。这条纪律不许为项目页破例。

### 2.3 与「设置页 / 关于页」的形态对齐

项目页同样是**内容体**：不自建 `Scaffold`、不自建 `AppBar`、根是 `mainAxisSize: min` 的 `Column`。
可参照 `pages\about_page.dart:89-95`（`Material(type: transparency)` + `Column(key: ValueKey('about-page'))`）
与 `app.dart:135-148`（仅在深链 `/about` 时才套一层 `Scaffold`）。

## 3. Schema 评估

### 3.1 结论

**零 schema 变更可行。** 三条判据：

1. 项目本体 + 里程碑 + 增量三表齐全，含 CHECK 与 CASCADE（§1.4）。
2. 「项目 → 待办」有真 FK（`todo.project_id`）。
3. 「项目 → 排期」有专用多态指针 + 专用索引（`plan_item.source_type='project'|'increment'` + `source_id` + `idx_plan_item_source`）。

### 3.2 已知缺口与应对（不靠改表解决）

| 缺口 | 影响 | 不改表的应对 |
|---|---|---|
| `plan_item` 无 `project_id` | 不能直接 `WHERE project_id` | 一律走 `source_type='project'/'increment'`；封装成仓储方法 `listByProject(projectId)`，把这条 SQL 只写一次 |
| `project` 无进度百分比列 | 不能存「70%」 | 进度**派生**：`已达成的里程碑数 / 里程碑总数`；无里程碑时显示 `—`，不显示 `0%`（0% 会被误读成"有里程碑且一个都没达成"） |
| `project` 无颜色/图标列 | 无法给项目配色 | 用 `project.domain` 派生一个稳定色相（对 `domain` 做哈希取模），或干脆不配色 —— 本项目已有 `AppTokens` 纪律，**不新增色值** |
| `project_increment` 无「停滞天数」列 | 无法存「已停滞 3 天」 | 运行时算：`today - max(increment.date)`；建表注释（`:345`）要求的「连续 3 天无增量触发温和停滞提示」也按此派生 |

### 3.3 为什么不做「加一张项目进度快照表」

因为 `snapshot_meta`（`docs\schema_v1.sql:453`）已经承担快照语义，再建一张表属重复；且本项目
的进度是**可派生**的，派生值存库会引入「存的值和事实不一致」的经典缺陷。派生，不存。

## 4. 与计划主页面的联动模型

共设计 **3 种**模型。每种都给出：触发点、读写路径、UI 落点、验收判据、风险。

### 4.1 模型 L1 · 排期联动（项目 → 今日方格）

**语义**：在项目详情里写一条「下一步动作」，直接成为今日（或指定日）的方格条目。

**通道**：`plan_item` 建行时写 `source_type = 'project'`、`source_id = <project.id>`（若来源是某条增量，
则 `source_type = 'increment'`、`source_id = <increment.id>`）。

**为什么不复用 `source_todo_id`**：那是待办专用列（`docs\schema_v1.sql:129` + FK `:...plan_item_source_todo_fk`），
语义不同，借用会导致待办与项目在统计里互相污染。

**UI 落点**
- 项目详情「增量流」每条记录右侧一枚 `→ 今天`；
- 项目详情头部一枚 `＋ 排进今天`（不绑定某条增量时用 `source_type='project'`）。

**验收判据**
- 点击后 `plan_item` 新增一行，`source_type` / `source_id` 逐字正确；
- 今日页 `DayGrid`（`widgets\timeline\day_grid.dart:46`）里该条目正常出现（条目 key 形如
  `day-grid-entry-${entry.id}`，`:373`）；
- 从方格删除该条目（`:651` `_delete`），**不**级联删除项目或增量（指针是单向的，删除只影响指针宿主）。

**风险**：`source_id` 是裸文本、无 FK 约束 ⇒ 项目被硬删后会产生悬空指针。应对：项目删除一律软删
（`deleted_at` 列已存在），并在读取时 join 过滤 `deleted_at IS NULL`。

### 4.2 模型 L2 · 积压联动（项目 → 待办池）

**语义**：待办池里挂上项目的条目，在项目详情里可一览；在项目详情里可把它们「捞进今日」。

**通道**：`todo.project_id`（`docs\schema_v1.sql:176`，FK `:190`，索引 `:195`）。

**UI 落点**
- 项目详情「关联区」第一段：该项目的待办列表，行内复用待办池的既有动作 `todo-pull-${todo.id}`
  （`pages\todo_pool_page.dart:523`）—— **复用同一个语义，不另造"捞进今日"的第二套实现**；
- 待办池侧增加只读项目徽标（这是《模块优化建议》M14 的内容，此处只登记依赖）。

**验收判据**
- 项目详情里的待办数与 `todo WHERE project_id = ? AND deleted_at IS NULL` 计数一致；
- 在项目详情点「捞进今日」后，待办池侧的条目状态与从待办池点同一动作的结果**完全一致**（同一条代码路径）。

**风险**：两处入口若各自实现，会出现「一边写 `source_todo_id`、一边漏写」的静默分叉。必须共用一个函数。

### 4.3 模型 L3 · 推进联动（增量 ↔ 复盘 ↔ 停滞提示）

**语义**：每天写完的复盘（`widgets\review_section.dart`），可一键成为某项目的**增量记录**；反过来，
项目详情里连续 3 天无增量时，在今日页给温和提示。

**通道**
- 写入：`project_increment` 追加一行（`progress` ← 复盘「做得好」+「学到了什么」，`blockers` ← 「不可控的事」，
  `next_step` ← 「下一步可控动作」）。字段来源见 `review_section.dart:34-41` 的 6 个字段定义。
- 关联：若当日的某条 `plan_item` 已经指向该项目（L1 的产物），则同时写 `project_increment.plan_item_id`
  （`docs\schema_v1.sql:347`，FK `ON DELETE SET NULL`），形成「这条路是为什么推进的」的可追溯链。

**UI 落点**
- 复盘区底部一枚 `→ 记到项目`（仅有 active 项目时出现）；
- 今日页右轨「闭环提示」面板（`app.dart:362` 的 `LoopHintPanel`）承载停滞提示 —— 该面板已存在，
  不新建面板。提示文案必须温和且可关闭，且**不得**变成红色警告（`project_increment` 的建表注释用的是
  「温和停滞提示」这个词）。

**验收判据**
- 断言增量记录**只追加**：任意操作路径下 `project_increment` 的既有行 `updated_at` 不变；
- 断言停滞判定为「今天 - 最近一条 date >= 3」时提示出现，`< 3` 时不出现；
- 断言提示关闭后当日不再出现（按日期粒度抑制，不是永久关闭）。

**风险**：把复盘整段文本搬进增量，等于同一份内容存两处。应对：增量只存**派生摘要**（各取首句或前 N 字），
并在 UI 上明确标注这是摘录；原文仍在 `day_log`，两处都可点回原处。

## 5. 三种模型的取舍

| 模型 | 数据成熟度 | 实现成本 | 用户价值 | 建议批次 |
|---|---|---|---|---|
| L1 排期联动 | 通道齐备（`source_type` + 索引） | 中（约 120 行） | **最高**：让「项目」真正进入每日工作 | P0 |
| L2 积压联动 | 通道齐备（真 FK） | 低（约 60 行，可复用待办池动作） | 高：项目不再是孤岛 | P0 |
| L3 推进联动 | 通道齐备（FK + 复盘字段） | 中高（约 150 行） | 高但依赖 L1 先有 `plan_item` 关联 | P1 |

**推荐落地顺序：L2 → L1 → L3。**
理由：L2 成本最低且不改用户体验心智（只是多一个筛选维度），先拿到「项目里有东西」的实感；
L1 一上，项目就接进了每日主循环，是最关键的一刀；L3 依赖 L1 的 `plan_item_id` 才有意义，必须最后。

## 6. 交互规格要点

1. **状态与归档是两维**：`status`（active/paused/done/cancelled）与 `archived`（0/1）都有 CHECK 约束
   （`docs\schema_v1.sql:298` 段）。UI 上状态是徽标，归档是折叠区，**不许合并成一个下拉**。
2. **增量不可编辑**：建表注释写明「每次推进只追加一条，不修改历史」。若写错了，允许追加一条更正记录，
   不提供编辑入口。
3. **进度不存百分比**：见 §3.2。显示 `3/5 里程碑`，不显示 `60%`。
4. **空态必须是动作**：无里程碑时给「加第一个里程碑」，无增量时给「写第一条增量」，
   不写「暂无数据」（参照 `pages\habits_page.dart:92` 的空态 key 纪律）。
5. **删除必须软删**：`deleted_at` 列在三张表里都有，硬删会打断 `plan_item.source_id` 的悬空指针链。

1. **开了也点不出东西**。`app.dart:283-297` 的 `_content()` 没有 `'projects'` 分支，翻成 `enabled: true`
