## 〇、先回答四个问题

| 问题 | 结论（一句话） |
|---|---|
| **电脑和手机怎么同步？** | 本地 SQLite 为唯一真相源 + **记录级增量同步（oplog）**，走**三条可插拔通道**：局域网直连（零成本最快）／WebDAV 自有通道（零成本通用）／公共中继服务（开箱即用）。**绝不同步活 SQLite 文件**。 |
| **有没有稳定的免费服务器存放所有使用者的云端数据？** | **有，但没有一个能单独扛全部**：最现实的是 **Cloudflare Workers + D1/Durable Objects + R2**（自建公共中继 + 对象存储），国内用户走 **七牛云**（10GB 免费存储 + 10GB/月 CDN 回源）。⚠️ **没有任何免费层是「永久稳定」的** —— 2026 年 Oracle 免费额度被砍半、Supabase 免费版 7 天不活动自动暂停、Cloudflare/Koyeb 都有闲置回收。**所以架构必须做到「服务消失时，用户数据仍然完整」。** |
| **分别存在电脑和手机，怎么同步更稳？** | 见第四章「稳定性七件套」：**双向增量 + 幂等重放 + 墓碑删除 + 冲突可回溯 + 服务端可回滚 + 本地永远可导出 + 断网可工作**。核心不是「怎么传」，而是「传丢了/传重了/传冲突了怎么办」。 |
| **备份与导出要不要进开发功能？** | **要，而且必须在 MVP 阶段做**（v0.2 模块 7）。理由：① 调研显示 uhabits / mhabit / streak / flow-dashboard **全部**支持导出 SQLite/CSV，「数据不锁死」是用户敢长期投入的前提；② 同步机制本身就是「可能失败」的机制，备份是它的兜底；③ 实现成本极低（SQLite 单文件 = 天然可导出）。 |

## 一、为什么不能用「同步数据库文件」——必须先立这条规矩

### 1.1 三种朴素方案的问题

| 朴素方案 | 致命问题 |
|---|---|
| **A. 把 SQLite 文件丢进 OneDrive / 百度网盘 / iCloud** | ① 文件级同步会**整体替换**目标文件，两端并发写必然产生「撕裂库」；② 你的库里存在大量**派生数据**（连续天数缓存、标签倒排、统计缓存），它们与源数据在两个设备上**必然不一致**；③ 思源笔记（siyuan）公开禁止第三方同步盘，原因正是块级引用索引会被同步盘损坏。**这不是配置问题，是结构问题。** |
| **B. 定期整库覆盖上传** | 后上传的设备会把先上传设备的改动**整体抹掉**；用户无法知道自己覆盖掉了什么；一旦出错无法定位是哪一次覆盖导致的。 |
| **C. 双向整库合并** | SQLite 没有内置合并语义，合并要么靠时间戳逐表（等于自己写一遍 oplog），要么靠 SQL 冲突规则（复杂且易错）。 |

### 1.2 本产品的结论

> **本地 SQLite 是唯一真相源；同步的单位是「记录级增量」，不是「文件」。**
> 派生数据（连续天数、聚合统计、标签倒排）**只存本地、不同步、新设备重算**。

这一条如果破了，后面所有同步逻辑都会退化成「如何在损坏的库上做恢复」，救不回来。

## 二、同步协议设计（v0.2 落地规格）

### 2.1 数据基础

所有业务表统一携带：`id (UUIDv7)`、`created_at`、`updated_at`、`deleted_at`（墓碑）、`origin_device_id`、`rev`。

- **UUIDv7** 而非自增整数：不同设备各自生成不会碰撞，且**时间有序** → 增量拉取可以用 `updated_at > cursor` 或 `id > cursor` 双保险。
- **墓碑删除**：删除绝不物理删行，只写 `deleted_at`。否则「A 端删了、B 端还留着」会永久打架。

### 2.2 操作日志（oplog）

```
oplog(id INTEGER PK AUTOINCREMENT,
      entity_table TEXT, entity_id TEXT,
      op TEXT,              -- upsert | delete
      payload TEXT,         -- 该行的字段级变更（JSON diff）
      lamport INTEGER,       -- 逻辑时钟，用于确定性排序
      device_id TEXT,
      created_at INTEGER,
      synced INTEGER DEFAULT 0)
```

**关键设计：字段级 diff，而非整行快照。**
理由：冲突发生在字段级。若用户在电脑改了「成果」字段、在手机改了「提醒时间」字段，字段级 diff 可以**两者都保留**；整行快照则必然丢一边。

### 2.3 同步握手流程（每次同步）

```
① 客户端上报：device_id + 上次同步游标(cursor) + 本地待推送 oplog
② 服务端响应：本次需拉取的增量（entity + 字段级 diff，按 lamport 排序）
③ 客户端应用增量（幂等：按 entity_id + field 逐字段写入，重复应用无副作用）
④ 客户端上报已应用的游标 → 服务端推进 cursor
⑤ 服务端回收已推送的 oplog（保留 N 天用于回溯）
```

**幂等性是硬要求**：网络重传、客户端崩溃重试、用户手动点「立即同步」，都必须能安全重复执行。

### 2.4 冲突策略

| 冲突类型 | 策略 |
|---|---|
| 不同字段并发修改 | **字段级 LWW**：按 `updated_at`（毫秒）+ `device_id` 字典序兜底打平 → 天然无冲突，无需人工介入 |
| 同一字段并发修改 | LWW + **保留被覆盖值到冲突箱**（本地可查「此字段曾被另一台设备改为 X」） |
| 多行文本并发修改（日志正文 / 复盘） | **不自动合并**：保留双方版本，用户在冲突提示里选一个或手动合并。**理由：单人多设备场景引入 CRDT（Automerge/Yjs）会把代码量和调试成本抬高一个量级，收益为零** |
| 删除 vs 修改 | 删除优先，但保留内容到「最近删除」区 30 天，可恢复 |

> **判定依据**：CRDT/OT 只在「多人同时编辑同一段文本」时才有必要。PractiLog 是**单人多设备**，LWW + 冲突可回溯足够，而且更容易测试与排障。调研中 joplin / siyuan / logseq 走的都是「块/文件级 + 人工介入解决冲突」，也印证了这个判断。

### 2.5 同步必须自带的可观测性

- 每次同步结束显示：**推 N 条 / 拉 M 条 / 冲突 K 处 / 最后同步时间**
- 设置页显示：各设备列表（名称、最后在线、上次同步版本）、手动「立即同步」、按设备「踢下线」（清其游标）
- 同步失败必须有**可见提示**，绝不能静默吞掉

## 三、三条通道的技术选型

### 3.1 通道 A：局域网直连（推荐默认，零成本、最稳）

**场景**：PC 与手机在同一 Wi-Fi 下 → 扫码配对 → 直接互传。

**技术实现**（参考调研中 MyBrain 的成熟做法：二维码配对 + NSD 服务发现 + WebSocket + AES-GCM）
- PC 端开一个监听端口（随机高位端口），广播 NSD/mDNS 服务名 `PractiLog-Sync-<短码>`
- 手机扫描 PC 上的二维码（含主机 + 端口 + 一次性令牌）→ 建立 WebSocket
- 通道内数据用 AES-GCM 加密，密钥由二维码承载
- 传输走自实现的增量协议（oplog 双向），**与公共中继同一套协议**，只是传输层不同

**优势**：完全不经过互联网中转 → 速度最快（局域网带宽）、延迟最低、**不需要任何服务器与账号**、不会被服务商政策变更打断。
**验证依据**：MyBrain（二维码配对 + NSD + WebSocket + AES-GCM）、SwashbucklerDiary、moodiary 三个项目都实现了局域网直连（≥3 个项目验证）。

### 3.2 通道 B：WebDAV 自有通道（零成本、最通用）

**场景**：用户有自己的 NAS / 坚果云 / 任意 WebDAV 服务 → 填地址 + 账号密码即可。

**技术实现**
- 客户端按需生成 `oplog` 增量包与每日快照包，上传到 ` PractiLog/` 目录下的子目录
- **走「增量文件 + 快照文件」，绝不同步活库**
- 目录结构：
  ```
  /PractiLog/
    ├── device/<device_id>/oplog/<seq>.jsonl   # 每设备的增量日志
    ├── device/<device_id>/manifest.json       # 该设备已上传的游标
    └── snapshots/YYYYMMDD-HHmm.db.zst        # 每日快照（压缩）
  ```
- 冲突由客户端本地解决（各自拉取对方的 oplog 后按 LWW 合并），**服务端只当 dumb storage**（这正是 WebDAV 的优势：无需服务端逻辑）

**优势**：**零运维、零成本、用户掌控数据存放位置**（调研中 mhabit / moodiary / SwashbucklerDiary / super-productivity ≥4 个项目用 WebDAV）。
**注意事项**：
- 坚果云等免费 WebDAV 有**速率限制与体积上限**，只适合日志这类小数据（建议开启「仅同步增量」而非整库）
- WebDAV 目录锁与部分实现对 `PUT` 覆盖不友好 → 用**内容哈希命名 + 不可变文件名**避免互相覆盖

### 3.3 通道 C：公共中继服务（开箱即用，需自建）

**场景**：用户不想折腾 NAS、不想填 WebDAV → App 内点一下「开启云同步」，输入另一台设备的同步码即可。

**关键决策：不做账号体系。**
- 首次开启同步 → 生成 **12 位同步码**（= 设备密钥对）
- 另一台设备输入同步码 → 配对完成
- 服务端只存**密文或明文（取决于是否做 E2EE）**，但**不存手机号、邮箱、姓名等任何身份信息**
- 用户可随时「轮换同步码」「注销远端数据」
> 理由：调研中「离线优先 + 无账号 + 无遥测」几乎是全领域共识（≥3 个项目，几乎全体）。账号体系是纯负担，且会立刻带来实名/隐私/合规问题。

**服务端组件选型（自建，零成本起步）**

| 组件 | 选型 | 免费额度（2026-11-06 检索） |
|---|---|---|
| API / 中继逻辑 | **Cloudflare Workers** | 免费 10 万请求/天、10ms CPU/请求；付费版 $5/月 含 1000 万请求/月、3000 万 CPU-ms、**解锁 Durable Objects** |
| 同步状态 | **Durable Objects (SQLite)** | 免费额度随 Workers 免费版；付费版 $5/月起 |
| 元数据索引 | **D1** | 免费 500 万行读/天、10 万行写/天、5GB 存储；单库最大 10GB、账号内最多 5 万库 |
| 对象存储（快照） | **R2** | 免费 10 GB-month 存储、100 万次 Class A 写、1000 万次 Class B 读、**出口流量免费** |
| 国内对象存储（备选） | **七牛云 Kodo** | 免费标准存储 10GB、GET 100 万次/月、PUT/DELETE 10 万次/月、CDN 回源流出 10GB/月、上传流量不限 |

> 来源：Cloudflare 官方定价页（R2 / Workers / D1 定价，公开费用截至 2026-01-01）；七牛云官方《免费额度须知》与《免费额度及查看方法》页面。

**为什么这套能在免费额度内撑住「所有使用者」**（粗算，假设单用户一年数据 5–20MB，压缩后 1–3MB）

| 资源 | 免费额度 | 单用户日均消耗（增量模型） | 可支撑用户数（保守） |
|---|---|---|---|
| R2 存储 | 10 GB | ~2 MB/用户（增量 + 周快照） | **数千量级** |
| D1 行写 | 10 万/天 | ~100 行/用户/天（oplog + 索引） | **约 1000 活跃用户** |
| D1 行读 | 500 万/天 | ~500 行/用户/天 | 远超 1000 用户 |
| Workers 请求 | 10 万/天 | ~40 请求/用户/天（增量 API） | **约 2000 设备** |

结论：**免费额度足够支撑「上千级活跃用户」的早期阶段**。真正的瓶颈不是额度，而是：
1. **D1 行写额度**（1000 用户量级）→ 需在用户量上升时改用 Durable Objects 承载同步状态 + R2 存 oplog 文件（避免逐行写 D1）
2. **国内访问质量**（Cloudflare 在国内延迟与稳定性不理想）→ 面向国内用户应把**对象存储放七牛云**，中继服务只做转发；或直接引导国内用户走 WebDAV / 局域网通道

### 3.4 三通道对比与推荐使用顺序

| | 局域网直连 | WebDAV | 公共中继 |
|---|---|---|---|
| 成本 | 0 | 0 | 0（自建） |
| 需要账号 | 否 | 否（用户自己的） | 否（同步码） |
| 速度 | 最快 | 中 | 中（国内需就近存储） |
| 稳定性责任方 | 用户自己 | 用户自己的服务商 | **你** |
| 适用 | 同 Wi-Fi 日常 | 有 NAS / 想自持 | 差旅 / 换设备 / 不想折腾 |
| MVP 优先级 | P0 | P0 | P1（可后置） |

**推荐引导路径**：首次启动时问一句「你的电脑和手机通常在同一个网络里吗？」→ 是则默认推荐局域网直连，否则推荐 WebDAV（附一份 3 分钟配置指引），仍嫌麻烦再给公共中继。

## 四、稳定性七件套（回答「分别存在电脑和手机，怎么才能更稳定同步」）

稳定性不是靠「多传几次」，而是靠**每一层失败都有确定的行为**。

1. **本地优先**：断网时 App 功能 100% 可用，写入只落本地 oplog，恢复网络后自动补传。同步永远是后台行为，绝不阻塞使用。
2. **增量 + 幂等**：重传、重复点击「立即同步」、崩溃重试，都不会产生重复数据或损坏。
3. **单调游标**：服务端为每个设备维护独立游标，`oplog` 序号单调递增 → 断点续传精确，不靠时间戳猜。
4. **墓碑删除 + 保留期**：删除同步得过去；服务端保留 oplog **30 天**用于回溯与「恢复误删」。
5. **冲突可回溯，不静默覆盖**：字段级 LWW 保证确定性；被覆盖的值进本地「冲突箱」，永远可查。
6. **服务端可回滚**：公共中继的数据库支持按日快照（Cloudflare D1 自带 **Time Travel，可回滚到过去 30 分钟的任意时点**；R2 可开对象版本），后台误操作可回退。
7. **本地永远可导出 + 自动快照**：即使中继服务明天消失，用户本地数据与导出包完整存在（详见第五章）。

### 4.1 必须提前防范的三个真实故障

| 故障 | 现象 | 对策 |
|---|---|---|
| **服务端长时间不可用** | 同步一直失败 | 客户端指数退避重试 + 明确的「离线模式」提示；**不弹错误骚扰**；本地 oplog 无限累积（上限保护：超过 N 条时提示导出备份） |
| **服务端数据被清空 / 账号被封** | 客户端拉到空数据 | **客户端必须校验「拉到的增量条数」与「本地期望」是否严重偏离**，偏离时**拒绝覆盖本地并报警**；服务端为每个同步码保存独立的加密备份链，用户可用同步码重新恢复 |
| **用户把库文件丢进网盘** | 数据库损坏 | 设置页与 README **明确禁止**；启动时做完整性检查（`PRAGMA integrity_check`）；检测到损坏时引导从快照恢复，并说明原因 |

## 五、备份与导出规格（v0.2 模块 7 的技术实现）

### 5.1 自动本地快照

| 项 | 规格 |
|---|---|
| 触发 | 每日首次启动后 / 写库后延迟 10 分钟 / 应用退出前 |
| 方式 | `VACUUM INTO 'snapshot.db'`（生成一致性快照，**不拷贝活库文件**） |
| 命名 | `snapshots/YYYYMMDD-HHmm.db` |
| 保留 | 最近 30 天每日一份 + 最近 12 周每周一份 + 最近 12 个月每月一份（滚动金字塔） |
| 索引 | `snapshot_manifest.json`：路径、时间、记录数、schema_version、**SHA-256** |
| 位置 | 应用数据目录；**不上传、不加密**（本地明文快照是正常的，除非用户开启加密导出） |

### 5.2 导出包规格

```
PractiLog-Export-YYYYMMDD-HHmm.zip
├── manifest.json     { schema_version, exported_at, device, counts{}, sha256{} }
├── practilog.db      SQLite 原库（可直接用任意 SQL 工具打开）
├── markdown/
│   ├── by-date/2026-11-06.md
│   ├── by-project/<项目名>.md
│   └── by-habit/<习惯名>.md
└── csv/
    ├── plan_item.csv, todo.csv, habit.csv, habit_checkin.csv,
    ├── project.csv, project_increment.csv, day_log.csv, reminder.csv
```

**工程约束**：
- 导出是**纯读操作**，使用只读连接；导出期间不阻塞写入
- 大数据量时分批导出 + 流式写 zip，避免内存峰值
- 导出完成后校验：行数与库内 `COUNT(*)` 一致、manifest 的 SHA-256 与实际文件一致
- 导入恢复前**自动给当前库打快照**；恢复为「导入为新库」，不覆盖当前库

### 5.3 WebDAV 自动备份

- 目标目录：`/PractiLog/backups/`
- 每天推送最新快照（压缩 zstd）+ 最近 7 天的增量 oplog
- 服务端保留策略由客户端控制（默认保留最近 10 份，删除旧文件）
- **与通道 B 的同步目录分开**（`/PractiLog/sync/` vs `/PractiLog/backups/`），避免互相干扰

### 5.4 加密备份

- 导出包可选密码加密：AES-256-GCM，密钥由 **Argon2id** 从用户密码派生
- **密码遗失 = 数据不可恢复**，UI 必须明确警示且不提供「找回密码」（服务端不存密钥是隐私承诺的必然结果）
- 加密导出包 = 上传到任何云盘都安全

## 七、推荐路线图

### 阶段 0（MVP，零成本零运维）
- ✅ 本地 SQLite + 自动快照 + 导出包（SQLite / Markdown / CSV / JSON）+ 导入恢复
- ✅ 局域网直连同步（自研协议，最先落地）
- ✅ WebDAV 同步（dumb storage 模式）
- ❌ **暂不做公共中继** —— 先把协议在两种通道上跑通，再上服务器

### 阶段 1（V1.1，开箱即用）
- 🆕 公共中继服务上线：Cloudflare Workers + Durable Objects + D1（索引）+ R2（快照）
- 🆕 同步码配对（无账号）、设备管理、冲突箱 UI
- 🆕 国内用户可选「存储位置：七牛云 / Cloudflare R2」
- 🆕 端到端加密同步（服务端只见密文）—— 这是隐私承诺的兑现，也是最大的信任杠杆

### 阶段 2（V1.2，商业化与规模）
- Workers Paid $5/月（解锁 Durable Objects 与 1000 万请求/月）作为成本兜底
- 同步码 → 可选「账号 + 设备绑定 + 跨设备恢复」
- 服务端多区域（国内就近节点）

## 八、隐私与安全清单

- [ ] 服务端**不收集任何身份信息**（无手机号 / 邮箱 / 实名）—— 与「无账号体系」一致
- [ ] 客户端不内置任何遥测；崩溃上报需用户主动开启
- [ ] 同步码 = 密钥，**服务端不存明文正文**（V1.1 达成 E2EE 后彻底闭环）
- [ ] 所有对外请求走 HTTPS；局域网通道用 AES-GCM
- [ ] 导出包加密默认关闭但**功能存在**，UI 说明「密码遗失不可恢复」
- [ ] 用户可一键「注销远端数据」（服务端删除该同步码下全部数据并回执）

## 九、需要在实现前确认的三个技术细节

1. **UUIDv7 库选型**：Dart 侧建议 `uuid` 包的 v7 支持（或自实现时间前缀）；需确认 Android 与 Windows 端一致性。
2. **SQLite 库选型**：Dart 侧 `drift`（编译到 SQLite，跨端一致，支持迁移与事务）；或 `sqflite` + `sqflite_common_ffi`（Windows 端需 ffi）。**推荐 drift**，因迁移框架与类型安全更强。
3. **Windows 通知**：需确认「应用关闭仍能提醒」的实现路径 —— 托盘常驻进程 + Windows 通知 API（Toast）最简单；完全退出后靠「计划任务唤醒」更可靠但实现复杂，**建议 MVP 只做托盘常驻**。
