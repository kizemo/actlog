## 一、技术选型

### 1.1 客户端：Flutter（推荐）

| 项 | 选择 | 理由 |
|---|---|---|
| 框架 | **Flutter 3.x（Dart）** | 一套代码覆盖 Windows + Android；调研中 mhabit / jotsy / moodiary 三个 Flutter 项目都实现了「Windows+Android+WebDAV」，路径已被验证 |
| 数据库 | **drift（SQLite）+ 迁移框架** | 类型安全、跨端一致、迁移可版本化；替代方案 sqflite + sqflite_common_ffi 在 Windows 端需 ffi，跨端行为差异多 |
| 状态管理 | Riverpod | 依赖注入与测试友好，适合「本地库 + 同步引擎」双数据源 |
| 通知 | flutter_local_notifications + Windows 托盘常驻 | Android 系统通知 + Windows Toast |
| Android 小组件 | home_widget 或自绘 AppWidget | 调研中 streak / mhabit 均用小组件直接打卡（高频需求） |

**备选：.NET 8/10 + Blazor Hybrid + SqlSugar** —— SwashbucklerDiary 已验证该路径同样可行。**若开发者 C# 熟悉度显著高于 Dart，走备选方案；领域模型、数据表结构、同步协议、开发计划完全不变，只换 UI 层。**

> 这是本计划**唯一的技术选型决策点**，建议在 P0 启动前用「1 天原型」验证：Windows 端 SQLite + 通知 + 托盘三件事是否跑通。

### 1.2 服务端（V1.1，MVP 不做）

Cloudflare Workers + Durable Objects + D1 + R2；国内用户对象存储可选七牛云。详见《同步与备份方案.md》第六章。

### 1.3 工程结构（建议）

```
practilog/
├── apps/
│   ├── desktop/            # Windows 壳、托盘、通知
│   └── mobile/             # Android 壳、小组件、通知
├── packages/
│   ├── core_domain/        # 领域模型（纯 Dart，无 IO）★ 双端共享
│   ├── core_db/            # drift schema + 迁移 + 仓储层
│   ├── core_sync/          # oplog 协议、冲突合并、通道抽象 ★ 双端共享
│   ├── core_backup/        # 快照、导出包、导入恢复
│   └── core_ui/            # 共享组件（计划条目、四宫格选择器、站会视图）
├── tools/
│   └── gates/              # 门禁脚本（迁移测试、导出等价校验、双设备同步测试）
└── docs/
```

**`core_sync` 必须与 UI 完全解耦** —— 协议要能在无 UI 的测试进程里跑完整同步循环。

## 二、阶段任务分解

| ID | 任务 | 人天 | 验收标准 |

## 三、质量门禁（每个阶段结束必跑）

| 门禁 | 内容 | 失败处理 |
|---|---|---|
| G1 分析 | `flutter analyze` 零 error / 零 warning | 阻断 |
| G2 单测 | 领域模型 + 仓储 + 算法（强度评分、衰减、LWW 合并）全绿，覆盖率 ≥70% | 阻断 |
| G3 迁移测试 | 空库 → v1；v0 库 → v1；迁移后数据行数与内容哈希一致 | 阻断 |
| G4 导出等价 | 导出包 → 导入新库 → 两库各表行数与内容逐行一致 | 阻断 |
| G5 同步幂等 | 同一增量重复应用 N 次结果一致 | 阻断 |
| G6 双端一致 | 同一场景在 Windows 与 Android 产出同 schema 数据 | 阻断 |
| G7 离线可用 | 断网状态下全部核心功能可用（含打卡、记录、导出） | 阻断 |
| G8 快照可恢复 | 随机删库 → 从最近快照恢复成功 | 阻断 |

> 所有门禁脚本放 `tools/gates/`，**每个脚本必须先有「故意破坏」的自测**（造坏数据 → 确认脚本会报错），否则门禁本身不可信。

## 四、测试策略

| 层级 | 范围 | 工具 |
|---|---|---|
| 单元测试 | 领域模型、强度评分算法、冲突合并、导出格式 | `flutter test` |
| 集成测试 | 仓储 + 迁移 + 快照 + 导出导入 | `flutter test integration_test` |
| 契约测试 | 同步协议在无 UI 进程中的完整循环 | `flutter test`（headless） |
| 真机场景 | 12 条用户路径（见下） | **人工 + 脚本双轨** |
| 性能 | 1 万条日志的列表滚动、导出耗时、启动耗时 | 手工基准 + 埋点 |

**12 条真机验收场景**（P6-4 逐条签字）
1. 全新安装 → 建习惯 → 打卡 → 日志出现带来源标记的回填行
2. 计划条目点优先级 → 四宫格选择器 → 选 Q2 → 保存 → 重开仍在
3. 待办 →「添加到今日计划」→ 标记完成 → 待办库同步变已完成
4. 今日页顶部站会三段显示正确
5. 复盘五段各自留白保存正常
6. 心态任一维度填 0 → 今日失守标记自动亮起
7. 长线项目动作不填成果也能保存；项目时间线出现该条
8. 计划提醒与习惯提醒互不影响（分别开关）
9. 应用完全关闭（非托盘）→ 计划任务路径是否仍提醒（若 MVP 不支持，明确写为已知限制）
10. 导出包 → 清库 → 导入 → 数据完全一致
11. 同 Wi-Fi 两台设备配对 → 手机打卡 → PC 日志出现该记录
12. WebDAV 同步 → 关 Wi-Fi 改数据 → 恢复网络 → 自动收敛

## 七、工期敏感性

| 情形 | 工期 | 应对 |
|---|---|---|
| 全量（P0–P6） | 14 周 | — |

**三条口径修正（后续按新口径执行）**

1. **表数量是 14 张，不是 13 张**。v0.2 实测：同步表 11 + 本机表 3。`docs/schema_v1.sql` 即唯一权威定义，G6 双端 schema 比对以它为准，不要再以文档叙述的表数为准。
2. **`hooks.user_defines` 必须写在 pub workspace 根 `pubspec.yaml`**。写在工作区成员包（如 `packages/core_db/pubspec.yaml`）会被**静默忽略** —— hook 缓存与配置按仓库根解析，成员包里的 define 不生效，表现为 `dart test` 长时间零输出后 exit 65。本轮踩到这个真实缺陷，已在根 `pubspec.yaml` 就地注释说明。
3. **D1 的 ATL 报错是环境缺陷，不是选型缺陷**。VS 2026（18.7.2）缺 ATL，`flutter_local_notifications_windows` 无条件 `#include <atlbase.h>` 导致 MSB8041。已用「借用本机 VS2022 ATL 的头/库搜索路径」零安装绕过；**禁止把 `atls.lib` 写进 `AdditionalDependencies`**（那才会触发 MSB8041）。
