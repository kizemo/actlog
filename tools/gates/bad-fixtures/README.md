# 坏数据样例（bad fixtures）

本目录存放**故意破坏**的样例，用来证明门禁脚本**真的有牙**。

> 没有验证过会咬的检查等于没有检查。

---

## 一、为什么要「故意破坏」

门禁脚本如果从来没有在坏数据上跑过，就无法区分两种情况：

* 门禁真的在检查（数据坏了 → 门禁红）
* 门禁只是走过场（数据坏了 → 门禁照样绿）

所以每个门禁都必须配套一份坏样例，并满足三条规矩：

1. **可复现**：坏样例由脚本**生成**，不是手工维护的二进制 / 文本快照 —— 否则样例本身会过期骗人。
2. **真数据**：坏样例基于**真实业务场景**构造（例：把心态度量改成 0、把象限改成非法值 `Q9`），而不是随手编的假数据。
3. **同一套断言**：坏样例必须跑**与门禁相同的核心断言**，否则「样例坏了」和「门禁会红」之间没有因果关系。

---

## 二、构造原理

坏样例的做法是：**在真实 schema 上做最小破坏，然后验证「约束确实失效」**，而不是凭空造一个畸形数据库。

具体手法（`self_test.mjs`）：

| 编号 | 坏样例 | 破坏对象 | 期望现象 |
|---|---|---|---|
| 1 | 中和全部 `CHECK` 约束 | 值域约束 | `quadrant='Q9'`、`mood_1=99`、`habit.type='crazy'` 全部被放行 |
| 2 | 中和全部 `UNIQUE` 约束 | 唯一性约束 | 同一个 `day_log.date` 可以重复插入 |
| 3 | 中和全部 `FOREIGN KEY` 约束 | 引用完整性 | 孤儿打卡（`habit_id` 指向不存在的习惯）可以插入 |
| 4 | 删掉 `oplog` 表（连同它的索引） | 表完整性 | 建库成功但只剩 13 张表 |
| 5 | 删掉 `idx_plan_item_date` 索引 | 查询路径 | 关键索引缺失 |

每个坏样例都做成**双向断言**：

* 完整 schema → 坏数据**必须被拒**（好路径）；
* 中和后的 schema → 坏数据**必须被放行**（证明这份坏样例真的破坏了约束，而不是「破坏失败」）。

只有双向断言都成立，才说明「这份样例有效」且「这份 schema 有牙」。

## 三、已知的两个坑（请勿重犯）

### 坑 1：跨行约束，按行正则会漏匹配

`docs/schema_v1.sql` 里相当一部分约束是**跨行**写的：

```sql
  CONSTRAINT plan_item_quadrant_check
    CHECK (quadrant IS NULL OR quadrant IN ('Q1', 'Q2', 'Q3', 'Q4')),
```

如果用「一行一条约束」的正则去匹配 `CONSTRAINT ... CHECK (...)`，这些约束会**整条漏掉** —— 表现为「破坏之后 schema 仍然拒绝 `Q9`」，也就是**坏样例根本没破坏到约束**，看起来像是门禁没牙。

**解法**：不要按行匹配，改用**括号配对扫描**定位约束文本的起止位置（`findConstraintSpans()`），正则在跨行时用 `\s` 而不是空格。

### 坑 2：直接删除约束文本会破坏逗号结构

把 `CHECK (...)` 那几行**删掉**看起来最直接，但会留下 `, )` 之类的语法错误；跨行约束 + 尾逗号组合起来更难做对。最终结果不是「约束失效」，而是「DDL 根本执行不了」—— 测的就不是想测的东西了。

**解法**：**中和（neutralize）而不是删除**。把约束体替换成恒真式，语法天然合法，语义却已失效：

```sql
CONSTRAINT plan_item_quadrant_check CHECK (1=1)
```

替换时从后往前替换（按 `start` 倒序），避免前面 span 的下标被前面的替换结果挪动。

## 四、怎么运行自检

```powershell
# 1) 坏数据自检：验证这些坏样例确实能破坏对应约束
node tools/gates/bad-fixtures/self_test.mjs

# 2) 门禁 G3 的「有牙测试」：门禁自己生成一份坏 schema，并要求自己必须失败
pwsh -File tools/gates/g3_migration.ps1
```

两个命令都应当在**退出码 0** 时表示「一切正常」：

* `self_test.mjs` 退出码 0 = 每条坏样例都确实破坏了对应约束（否则说明样例失效了）；
* `g3_migration.ps1` 退出码 0 = 门禁在**好 schema** 上通过，同时在**坏 schema** 上确实失败（否则门禁判定自己没牙并直接失败）。

单独看门禁在某一份坏 schema 上的表现：

```powershell
pwsh -File tools/gates/g3_migration.ps1 -SchemaPath <坏 schema 路径> -SkipToothTest
# 期望：退出码非 0，stderr 打印出具体是哪几条约束没牙
```
